### Scenario 1 (S1): Operations Revenue & Order Volume Threshold Report

#### Scenario Context
You are a data analyst at a food delivery platform. The operations team needs a report showing which restaurant partners earned more than Rs 1,00,000 in total revenue last month — but only for restaurants that received at least 50 orders.

#### Question
> Explain how you would use `GROUP BY` and `HAVING` together to produce this report. Why is `HAVING` more appropriate than `WHERE` for filtering on aggregated values? What would break in your query if you replaced `HAVING` with `WHERE`?

---

#### Comprehensive Answer

##### 1. How `GROUP BY` and `HAVING` Work Together for this Report
To produce this report, the granular transaction data stored in an orders table (where each row represents a single customer order) must be aggregated to the restaurant level:

1. **`GROUP BY restaurant_id, restaurant_name`**: Collapses all individual order records belonging to the same restaurant partner into a single grouped row.
2. **Aggregate Calculations**:
   - `SUM(order_amount)` computes the cumulative revenue generated by each restaurant.
   - `COUNT(order_id)` computes the total number of orders fulfilled by each restaurant.
3. **`HAVING` Filtering**: Evaluates conditions on the calculated aggregate metrics *after* the grouping operation. We specify:
   ```sql
   HAVING SUM(order_amount) > 100000 AND COUNT(order_id) >= 50
   ```
4. **Time Range Filtering (`WHERE`)**: The requirement specifies "last month". This row-level filter is placed in the `WHERE` clause before grouping occurs, ensuring only orders from the relevant billing cycle are summarized.

##### Example Production Query
```sql
SELECT 
    r.restaurant_id,
    r.restaurant_name,
    COUNT(o.order_id) AS total_orders_last_month,
    SUM(o.order_amount) AS total_revenue_last_month
FROM restaurants r
INNER JOIN orders o ON r.restaurant_id = o.restaurant_id
WHERE o.order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 1 MONTH)
  AND o.order_status = 'Delivered'
GROUP BY 
    r.restaurant_id, 
    r.restaurant_name
HAVING 
    SUM(o.order_amount) > 100000 
    AND COUNT(o.order_id) >= 50
ORDER BY 
    total_revenue_last_month DESC;
```

##### 2. Why `HAVING` is More Appropriate Than `WHERE` for Filtering on Aggregated Values
The distinction lies in the **SQL Logical Query Processing Order**:

$$\text{FROM} \longrightarrow \text{ON} \longrightarrow \text{JOIN} \longrightarrow \mathbf{WHERE} \longrightarrow \mathbf{GROUP\ BY} \longrightarrow \mathbf{HAVING} \longrightarrow \text{SELECT} \longrightarrow \text{ORDER\ BY} \longrightarrow \text{LIMIT}$$

- **`WHERE` executes at Step 4**: It scans raw individual table rows *before* rows are assembled into groups. At this stage, aggregate metrics like `SUM()` and `COUNT()` do not yet exist in memory.
- **`HAVING` executes at Step 6**: It operates strictly on the summarized result sets produced by `GROUP BY`. Because group boundaries and aggregate calculations are finalized by Step 5, `HAVING` can filter groups based on calculated summary metrics.

| Feature | `WHERE` Clause | `HAVING` Clause |
| :--- | :--- | :--- |
| **Execution Phase** | Before grouping (`GROUP BY`) | After grouping (`GROUP BY`) |
| **Operates On** | Individual physical rows | Aggregated groups of rows |
| **Accepts Aggregates?** | **No** (`SUM`, `COUNT`, `AVG` forbidden) | **Yes** (`SUM`, `COUNT`, `AVG` permitted) |
| **Primary Role** | Pruning input data set | Filtering summary output |

##### 3. What Breaks if `HAVING` is Replaced with `WHERE`?
If you attempt to write:
```sql
-- INVALID QUERY
SELECT restaurant_name, SUM(order_amount)
FROM orders
WHERE SUM(order_amount) > 100000 AND COUNT(order_id) >= 50  -- FAILS HERE
GROUP BY restaurant_name;
```

1. **Parser & Execution Engine Failure**: The MySQL engine immediately terminates with:
   ```text
   ERROR 1111 (HY000): Invalid use of group function
   ```
2. **Root Cause**: The query optimizer cannot evaluate `SUM(order_amount)` when examining an individual row because a single row only holds its own `order_amount`, not the sum of all orders for that restaurant.
3. **If filtering on a column alias**: If you write `WHERE total_revenue > 100000`, MySQL will raise:
   ```text
   ERROR 1054 (42S22): Unknown column 'total_revenue' in 'where clause'
   ```
   because `SELECT` column aliasing occurs *after* `WHERE` evaluation.

### Scenario 2 (S2): Customer Insights Report & Inactive User Visibility

#### Scenario Context
You are building a customer insights report for a food delivery app. The marketing team needs a list of every registered customer and their most recent order details — even for customers who have never placed an order.

#### Question
> Which type of JOIN would you use to ensure all customers appear in the result, including those with no orders? Justify your choice by comparing it with INNER JOIN, and explain specifically what data would be lost if INNER JOIN were used instead.

---

#### Comprehensive Answer

##### 1. Selected JOIN Type
To satisfy this requirement, a **`LEFT OUTER JOIN`** (or simply **`LEFT JOIN`**) must be used, placing the `customers` table as the left table:
```sql
SELECT 
    c.customer_id,
    c.customer_name,
    c.city,
    latest_orders.order_id,
    latest_orders.order_date,
    latest_orders.order_amount
FROM customers c
LEFT JOIN (
    SELECT 
        customer_id,
        order_id,
        order_date,
        order_amount,
        ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC, order_id DESC) AS rn
    FROM orders
) latest_orders 
    ON c.customer_id = latest_orders.customer_id 
   AND latest_orders.rn = 1;
```

##### 2. Justification & Comparison with `INNER JOIN`
- **`LEFT JOIN` Mechanics**: A `LEFT JOIN` guarantees that **every record** from the left table (`customers`) is preserved in the final output. If a customer has one or more matching records in the right table (`orders`), the joined attributes are displayed. If a customer has **zero matching records** in `orders`, the customer’s identity attributes (`customer_id`, `customer_name`, `city`) remain intact, while all joined order columns (`order_id`, `order_date`, `order_amount`) are populated with `NULL`.
- **`INNER JOIN` Mechanics**: An `INNER JOIN` outputs only the mathematical intersection ($A \cap B$) of the two sets. It strictly requires the join condition (`c.customer_id = o.customer_id`) to evaluate to `TRUE`.

| Evaluation Aspect | `LEFT JOIN` (`customers` $\to$ `orders`) | `INNER JOIN` (`customers` $\Join$ `orders`) |
| :--- | :--- | :--- |
| **Customers with Orders** | Retained with order details | Retained with order details |
| **Customers with Zero Orders** | **Retained** (Order columns display `NULL`) | **Silently Eliminated** from output |
| **Set Theory Representation** | Preserves Universe $C$ ($C \cup (C \cap O)$) | Preserves only Intersection ($C \cap O$) |

##### 3. Specific Data Lost if `INNER JOIN` Were Used
If an `INNER JOIN` were utilized, **all zero-order customers would be completely excluded** from the query output. This introduces severe business consequences for the marketing team:
1. **Loss of Top-of-Funnel Conversion Visibility**: Marketing cannot determine the drop-off rate between registration/app download and first purchase.
2. **Inability to Target Churn Prevention & Activation Campaigns**: Marketing cannot isolate zero-order users to send targeted onboarding incentives (e.g., "Use code FIRST50 for 50% off your first meal").
3. **Skewed Customer Metrics**: Reporting average customer lifetime value, active customer ratios, and retention rates would suffer from survivor bias, artificially inflating user engagement statistics.

### Scenario 3 (S3): Delivery Performance Benchmark & Subquery Architecture

#### Scenario Context
You are designing a delivery performance dashboard. The business wants to identify delivery agents whose average delivery time is faster than the overall platform average, without using a temporary table or creating a new view.

#### Question
> Describe how you would write a subquery to find these agents. What type of subquery is most appropriate here — scalar, row, or table — and why? What would happen if you tried to place this subquery in the SELECT clause instead of the WHERE clause?

---

#### Comprehensive Answer

##### 1. Subquery Design & Query Structure
To find these delivery agents without temporary tables or views, we calculate each agent's average delivery time in the outer query and compare it against the global benchmark calculated via an embedded subquery in the `HAVING` clause:

```sql
SELECT 
    delivery_agent_id,
    agent_name,
    ROUND(AVG(delivery_time_mins), 2) AS agent_avg_delivery_time
FROM deliveries
GROUP BY 
    delivery_agent_id, 
    agent_name
HAVING 
    AVG(delivery_time_mins) < (
        -- Subquery: Computes the global platform benchmark
        SELECT AVG(delivery_time_mins) 
        FROM deliveries
    )
ORDER BY 
    agent_avg_delivery_time ASC;
```

##### 2. Subquery Classification: Why a Scalar Subquery is Appropriate
The required subquery is a **Scalar Subquery**.

- **Definition**: A scalar subquery returns exactly **one row and one column** (a single atomic value, such as `28.45` minutes).
- **Justification**:
  - The comparison operator `<` (strictly less than / faster than) is a binary comparison operator expecting a single scalar operand on its right-hand side.
  - A **Row Subquery** returns a single row with multiple columns (e.g., `(28.45, 'Surat')`), which cannot be compared with a single average number.
  - A **Table Subquery** returns multiple rows and columns (a relation), requiring multi-row operators like `IN`, `ANY`, or `ALL`. Using a table subquery here with `<` would trigger:
    ```text
    ERROR 1242 (21000): Subquery returns more than 1 row
    ```
  - Therefore, a scalar subquery producing `SELECT AVG(delivery_time_mins) FROM deliveries` is mathematically and syntactically the only correct choice.

##### 3. What Happens if Placed in the `SELECT` Clause Instead of `WHERE`/`HAVING`?
If placed in the `SELECT` list:
```sql
SELECT 
    agent_name,
    ROUND(AVG(delivery_time_mins), 2) AS agent_avg_time,
    (SELECT ROUND(AVG(delivery_time_mins), 2) FROM deliveries) AS platform_avg_benchmark
FROM deliveries
GROUP BY agent_name;
```

1. **Projection vs. Filtering**: The `SELECT` clause controls **projection** (which attributes appear in the columns), whereas `WHERE` and `HAVING` control **row selection/filtering** (which rows qualify for the final output).
2. **Behavioral Outcome**: Every delivery agent across the company will still be listed—both high performers and failing agents. The platform average will merely repeat as an informational column on every row.
3. **Failure of Objective**: The business mandate was to **isolate and identify** the fast delivery agents. Without filtering in `HAVING`, the business user receives an unfiltered list and must manually identify qualified agents.

### Scenario 4 (S4): Ranking Tied Restaurant Revenues in Surat (`RANK` vs `DENSE_RANK`)

#### Scenario Context
You are analysing order data for a food delivery company. The product team wants to rank the top 3 highest-revenue restaurants within each city. Two restaurants in Surat have the exact same revenue figure and you must decide how to number them.

#### Question
> Compare `RANK()` and `DENSE_RANK()` window functions for this use case. Which would you choose and why? Provide a brief example showing how each function would number three restaurants where two share the same revenue, and explain the practical impact of that difference on the product team's report.

---

#### Comprehensive Answer

##### 1. Core Comparison: `RANK()` vs `DENSE_RANK()`
Both `RANK()` and `DENSE_RANK()` are SQL window functions that compute positional rank based on a specified ordering expression within partitions. When two rows share identical values in the `ORDER BY` clause, both functions assign the same rank number to both rows. The fundamental difference lies in how subsequent ranks are handled:
- **`RANK()`**: Introduces **gaps** in the ranking sequence. If two entities tie for Rank 1, the next assigned rank is Rank 3 (skipping Rank 2). The rank reflects $(1 + \text{count of prior rows})$.
- **`DENSE_RANK()`**: Produces a **continuous, unbroken** integer sequence (1, 1, 2, 3...). It numbers distinct ordered values without skipping integers.

##### 2. Concrete Example: Three Restaurants in Surat
Consider three restaurants in Surat with the following monthly revenues:
- Restaurant A (Surat): ₹1,00,000
- Restaurant B (Surat): ₹1,00,000 *(Tied with A)*
- Restaurant C (Surat): ₹80,000

| Restaurant | City | Total Revenue | `RANK()` Output | `DENSE_RANK()` Output |
| :--- | :--- | :--- | :---: | :---: |
| **Restaurant A** | Surat | ₹1,00,000 | **1** | **1** |
| **Restaurant B** | Surat | ₹1,00,000 | **1** | **1** |
| **Restaurant C** | Surat | ₹80,000 | **3** *(Skips 2)* | **2** *(No gap)* |

##### 3. Recommendation & Practical Impact on the Product Team's Report

###### Recommendation: `DENSE_RANK()`
`DENSE_RANK()` is the recommended choice for competitive leaderboard and performance tiering.

###### Practical Impact Analysis:
1. **Impact of using `RANK()`**:
   - If the product team applies a filter `WHERE rank_num <= 3`:
     In our example, Restaurants A, B, and C are included (ranks 1, 1, 3). However, if there was a Restaurant D (₹70,000) and Restaurant E (₹60,000), filtering `WHERE rank_num <= 3` would include A (1), B (1), and C (3), cutting off D (4).
     More critically, if three restaurants tied for Rank 1 (1, 1, 1), the fourth restaurant receives Rank 4. Filtering `WHERE rank_num <= 3` would return only the 3 tied restaurants, completely omitting Rank 2 and Rank 3.
   - Stakeholders reading the dashboard frequently question data integrity when Rank 2 is absent: *"Why is there a Rank 1 and a Rank 3, but no Rank 2?"*
2. **Impact of using `DENSE_RANK()`**:
   - Recognizes **revenue tiers**. Restaurants A and B occupy the Top Tier (Rank 1). Restaurant C is rightly recognized as the 2nd Highest Revenue Earner (Rank 2).
   - Allows the product team to reward distinct revenue benchmarks without skipping numerical awards. If the product team has an explicit restriction of exactly 3 physical slots, they must be aware that ties under `DENSE_RANK()` with `<= 3` can yield more than 3 total rows.

### Scenario 5 (S5): CRM Customer Segmentation via `CASE WHEN` & Short-Circuit Evaluation

#### Scenario Context
You are writing a CRM query for a food delivery startup. The customer success team wants each customer labelled as 'Platinum', 'Gold', or 'Standard' based on total lifetime spend — above Rs 5,000, between Rs 2,000 and Rs 5,000, and below Rs 2,000 respectively — directly in the query output without creating a new table.

#### Question
> Explain how you would use CASE WHEN to generate this classification column. If a customer's total spend is exactly Rs 5,000, which tier will they fall into, and how does the order of your WHEN conditions control that outcome?

---

#### Comprehensive Answer

##### 1. Implementation of the `CASE WHEN` Expression
The SQL `CASE WHEN` construct provides conditional branching logic directly within query expressions. In this scenario:

```sql
SELECT 
    c.customer_id,
    c.customer_name,
    SUM(o.order_amount) AS lifetime_spend,
    CASE 
        WHEN SUM(o.order_amount) > 5000 THEN 'Platinum'
        WHEN SUM(o.order_amount) >= 2000 THEN 'Gold'
        ELSE 'Standard'
    END AS customer_tier
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY 
    c.customer_id, 
    c.customer_name
ORDER BY 
    lifetime_spend DESC;
```

##### 2. Tier Assignment for Exactly Rs 5,000
A customer with a lifetime spend of **exactly Rs 5,000** will fall into the **'Gold'** tier.

- **Boundary Condition Analysis**:
  - The business specification defines Platinum as *"above Rs 5,000"* ($> 5000$).
  - For a value of 5,000, `5000 > 5000` evaluates to **FALSE**.
  - The evaluator advances to the next clause: `WHEN SUM(o.order_amount) >= 2000`.
  - Because 5,000 is greater than or equal to 2,000, this condition evaluates to **TRUE**.
  - Therefore, the customer is assigned to **'Gold'**.

*(Note: If the business intended 5,000 to be Platinum, the condition would have been formulated as `>= 5000`, in which case it would evaluate to TRUE at the first branch).*

##### 3. How the Order of `WHEN` Conditions Controls the Outcome
SQL `CASE` statements operate using **short-circuit sequential evaluation**:
1. The engine checks expressions strictly from **top to bottom**.
2. The moment a condition evaluates to `TRUE`, the engine returns the corresponding `THEN` value and **immediately exits the `CASE` block**, skipping all subsequent `WHEN` and `ELSE` branches.

###### Demonstrating Order Dependency & Flawed Logic
Consider what happens if an analyst incorrectly reverses the order of conditions:
```sql
-- FLAWED IMPLEMENTATION
CASE 
    WHEN total_spend >= 2000 THEN 'Gold'      -- Evaluates FIRST
    WHEN total_spend > 5000 THEN 'Platinum'   -- NEVER REACHED FOR PLATINUM SPENDERS
    ELSE 'Standard'
END AS customer_tier
```
- Suppose a VIP customer spends ₹25,000.
- When reaching `WHEN total_spend >= 2000`, the comparison `25000 >= 2000` is **TRUE**.
- The engine immediately assigns `'Gold'` and terminates the `CASE` evaluation.
- The `WHEN total_spend > 5000` check is **dead code** and will never execute.
- **Rule of Thumb**: When writing numerical range classifiers without explicit double-ended bounds (`BETWEEN`), conditions must always be ordered from **most restrictive to least restrictive** (descending numerical thresholds: `> 5000` before `>= 2000`).

### Scenario 6 (S6): Storage Engine Indexing, Query Optimization & Trade-Offs

#### Scenario Context
You are optimising a slow-running analytics query for a food delivery platform. The query joins four large tables and applies a GROUP BY across 10 million rows, taking over 30 seconds. A colleague suggests adding an index on the JOIN column used most frequently.

#### Question
> Explain what a database index does at the engine level and why it would speed up this specific query. Are there scenarios where adding an index could actually hurt performance? What trade-off must you evaluate before indexing every column in a large table?

---

#### Comprehensive Answer

##### 1. What a Database Index Does at the Storage Engine Level
In modern relational storage engines (such as MySQL's InnoDB), an index is a self-balancing tree structure, predominantly a **$B^+$-Tree** (B-Plus Tree).

```
                  [ Root Page: Key 500 | Key 1000 ]
                           /          |         \
     [ Internal Page: Key 100-499 ]  ...   [ Internal Page: Key 1001-2000 ]
              /              \
 [ Leaf: Keys + Row Pointers ] <---> [ Leaf: Keys + Row Pointers ]  (Doubly Linked)
```

1. **Physical Layout**:
   - Non-leaf (internal) nodes store search keys and memory/disk page pointers.
   - Leaf nodes reside at uniform depth and store the indexed key along with row pointers (in InnoDB secondary indexes, the pointer is the table's Primary Key / clustered index key).
   - Leaf nodes form a doubly-linked list, allowing sequential range scans.
2. **Elimination of Full Table Scans**:
   - Without an index, evaluating `JOIN ON orders.customer_id = customers.customer_id` across 10 million rows forces InnoDB to execute a **Full Table Scan ($O(N)$)**. Every 16 KB data page must be loaded from NVMe/HDD storage into the InnoDB Buffer Pool and checked sequentially.
   - For a four-table join, this degenerates into a nested loop reading tens of millions of pages ($O(N \times M)$), resulting in massive disk I/O, CPU consumption, and execution times exceeding 30 seconds.
3. **Speedup Mechanism for the 4-Table Query**:
   - With a $B^+$-Tree index on the foreign key join column, lookup complexity drops from $O(N)$ to **$O(\log N)$**. For 10 million rows, tree depth is typically only 3 or 4 page traversals.
   - The query planner switches from a Block Nested Loop / Table Scan to an **Index Lookup (`ref` or `eq_ref`)**. Instead of scanning 10 million records for every outer table record, it performs direct indexed page fetches, reducing query time from 30+ seconds down to milliseconds.

##### 2. Scenarios Where Adding an Index Can Hurt Performance

1. **Severe Degradation of Write Operations (DML Latency)**:
   - Every `INSERT`, `UPDATE` (of indexed columns), and `DELETE` incurs secondary maintenance costs.
   - When an order arrives, MySQL must write to the clustered index and update every single secondary $B^+$-Tree index.
   - This causes random I/O, node splits, and page rebalancing. In write-heavy OLTP environments (e.g., thousands of food orders per second), superfluous indexes severely throttle write throughput.
2. **Low-Cardinality / Low-Selectivity Columns**:
   - Indexing columns with very few distinct values (such as `is_active` [0/1], `gender` [M/F], or `delivery_status`) hurts performance.
   - If a status matches 70% of rows, using an index requires jumping back and forth between secondary index leaf pages and the primary key clustered index (Random Bookmark Lookups). The optimizer often calculates that a sequential table scan is faster than random index lookups, rendering the index useless overhead.
3. **Buffer Pool Cache Thrashing**:
   - Indexes consume memory in the InnoDB Buffer Pool. If massive, unneeded indexes compete with actual table data pages for cache space, hot transaction pages get evicted to disk, degrading overall database performance.

##### 3. Trade-offs to Evaluate Before Indexing Columns in a Large Table

| Evaluation Vector | Low Index Count (Under-Indexed) | High Index Count (Over-Indexed) | Optimal Strategy |
| :--- | :--- | :--- | :--- |
| **Read Speed (SELECT)** | Slow (Table scans, high latency) | Fast for specific lookups | Index high-frequency `JOIN`, `WHERE`, `ORDER BY` predicates |
| **Write Speed (INSERT/UPDATE)** | Fast (Minimal overhead) | Slow (Multi-tree updates, page splits) | Keep secondary indexes minimal on OLTP tables |
| **Storage Footprint** | Small (Data pages only) | Massive (Index sizes often exceed table data) | Monitor `information_schema.innodb_buffer_page` usage |
| **Optimizer Overhead** | Fast plan selection | Planner overhead increases evaluating index choices | Use Composite Indexes (`customer_id, order_date`) to cover queries |

**Final Recommendation**:
Before adding an index, run `EXPLAIN FORMAT=JSON` or `EXPLAIN ANALYZE` to inspect cost estimates, verify join types (`ref` vs `ALL`), check selectivity, and test composite indexes that provide index covering for both the `JOIN` and `GROUP BY` clauses.
